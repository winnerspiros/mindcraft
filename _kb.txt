# Known bugs + permanent fixes

Extracted verbatim from SKILL.md, which had grown past its size cap. One line per
bug, each a rule that must not be re-learned the hard way. Grouped by area.

- Boss summons need explicit consent: !summon wither/ender_dragon refuses without a consent word and caps at 1 — unsupervised boss spawns grief the server and death-loop the bot into crash restarts, and each death wedges the next dig into a death-race timeout.
- action_manager catch must never cleanKill on 'Digging aborted' (mid-dig interrupt or death race): return it as an interrupt with the marker cleared and no reliability record — treating a stop/death race as an action failure turns every mid-swing interrupt into a systemd restart loop.
- Death-bug: player .dat Health 0.0 + death screen blocks /login ("Authentication time expired"). Fix: set Health to max in .dat (backup first); EasyAuth PrepareSpawnTask$ReadyMixin.saveDeadState patched to setHealth(getMaxHealth) on join.
- Spectator-trap: UwU file playerGameType flipped to 3 (invisible, gray tab). Set back to 0 (survival) with bot stopped.
- Spawn-trap: spawn-point worldspawn arg order is (x z y) in the bot code — verify before use. Suffocation escape must NOT /tp (Invalid-move kick); use resistance + walk-out. Respawn recovery must NOT /tp to death spot; walk + pickup + _reArmor only.
- Server wedge diagnosis: trust the JVM thread dump, never temporal correlation. Signature is RCON-accepting-but-empty + spark world-stat timeouts every 10s + server thread CPU ~0. Two distinct park states observed: (a) WAITING Connection.syncAfterConfigurationChange (config-phase promise never completes), (b) parked on io/netty/channel/DefaultChannelPromise (a stalled network write future — NOT the login path at all). Kick bursts preceding a wedge do not prove the login path caused it — a fast-rejoining player must never be able to wedge the server, so treat burst-correlation as a lead, never a verdict. Tick-starvation baseline on 1 OCPU: a boot-time `Can't keep up! Running 6000ms+ behind` with zero players proves the tick loop starts underwater; per-login chunk sends are the heaviest server task, so a join burst (spawn teleports + 9x9 chunk stream + immediate AI pathfinding) drowns it further until futures time out and the loop stalls silently — fix per-login cost (settle holds, ack throttling), not rejoin speed. On Semeru OpenJ9 jstack cannot attach ('HotSpot VM not loaded') — read the javacore*.txt the JVM dumps (3XMTHREADINFO + 3XMTHREADBLOCK lines give thread state + waiter identity). Trigger the dump BEFORE stopping the server (SIGQUIT dumps a javacore without killing on OpenJ9) — a dump taken during shutdown is contaminated evidence: a `Server Shutdown Thread` + `SIGTERM handler` in the thread list means the stop was already in progress, and a Server thread parked on a Netty promise then is just connection-draining, not the wedge. Correlate the dump timestamp against the last non-spark log line; silence with only spark timeouts means the tick loop stopped with zero error output. Only kill -9 + start unwedges (rcon stop / systemctl stop hang; jcmd/jstack unresponsive). DEADLOCK TRIANGLE (proven by live jcmd dump): a mod doing a BLOCKING world query on the Netty IO thread inside a movement handler (LightAntiCheat isInsideSolid called ServerChunkCache.getChunk().join() from onMovePlayer) parks the IO thread; the Server thread parks on a channel promise needing that IO thread -> mutual wait, zero error output, RCON still answers. Never block on chunk/world futures on the Netty IO thread in a mixin — use loaded-only block queries or run off-thread. When a wedge recurs, check Netty IO stacks for mod frames before blaming anything else; the offending mod comes OUT until rewritten. Ops order: bot OFF first, server up + Done + RCON list, user confirms in-game and stable, THEN bot back. Kick-rejoin backoff (IMPLEMENTED in agent.js onDisconnect): 60s wait after an Invalid-move kick, 20s after any other disconnect, before process.exit lets systemd restart — verified live via `[LoginGuard] rejoin backoff 60s (movement-kick)`. Spawn-settle: 20s hold after gearUp before AI actions start (`[LoginGuard] spawn-settle 20s`), so the tick loop drains the join burst before pathfinding piles on.
- 26.3 Invalid-move kick-loop causes found (jar truth): (1) cheat-/tp paths (server teleports the client stack can't echo) — all neutered to walk; (2) blind pathfinder goto with destructive movements into walls (moved-wrongly) — no-path now stays put + returns false; (3) bare look folded into position_look raced the per-tick gate — reverted to plain look writes (look never touches receivedPositionThisTick); (4) mineflayer idle heartbeat (position resend every 1s while standing still) landing second-in-window after a look/echo — removed, send only on real moves; (5) back-to-back physics ticks emitting two position_looks into one server tick window (tick_end is async; 9-45ms gaps proved) — client send gate max ONE position-bearing send per 120ms (physics.js gatePosSend; bare look exempt). Jar truth for the pairing: handleClientTickEnd clears receivedPositionThisTick (and receivedMovementThisTick, resetting known-movement to ZERO when nothing arrived), so every position send must be immediately followed by tick_end — physics.js sendTickEnd() already does this after each write. (6) echo handler re-enabling physics mid spawn-burst (7+ spawn teleports in <1s, MFconf probe proved) — whose echo position_look + updatePosition sends collided in one tick window -> invalid_player_movement kick. Re-enable physics only AFTER the burst quiets — 5s quiet timer reset on every server teleport (armBurstQuiet in the echo handler + spawn/death/login freeze paths), re-arm only after 5s with zero teleports — never per-echo and never on the 'spawn' event (the spawn event fires at the START of the placement burst, so re-arming on it re-arms mid-burst; walk-death proved looks flowing 49ms apart for 48s with spawn-event re-arm); never block teleport_confirm in spawn-hold (server requires it to finish placement); (7) collectblock collect() drives sprint-jump strafe legs at the block face (d1.0-1.4 fall deltas) because the plugin's constructor builds its OWN `new Movements(bot)` with sprint+parkour defaults and calls setMovements — overwriting the bot's WALK-ONLY movements. So collect-via-dig only (goToPosition walk + bot.dig + pickupNearbyItems, never bot.collectBlock.collect) until collectblock accepts injected WALK-ONLY movements — verified in its CollectBlock.js source (constructor + collect both setMovements); restore ONLY on that condition. (8) pathfinder sprint during walks — EVERY fresh `new pf.Movements(bot)` (goToGoal both branches, goToPosition, followPlayer, collect/pickup/breakBlock/place paths) defaults to allowSprinting=true AND allowParkour=true and must be pinned down. Mechanism (mineflayer-pathfinder follow-state): allowSprinting adds exactly two behaviors — flat sprint on straight lines, and sprint-JUMP over gaps. A live far-leg trial of flat-sprint-only (allowSprinting=true, allowParkour=false) still drew a server `moved wrongly` WARN (no disconnect, she stayed on) — so on this 26.3 stack treat sprint as per-leg opt-in, not blanket-on. She is LAC-exempt (her offline UUID is the exempt one), so the vanilla moved-wrongly gate cannot touch her; worst case is LAC's own speed_threshold=0.6 setback-only (straight sprint ~0.28/tick, sprint-jump ~0.36, both under). Keep WALK default everywhere and arm sprint/parkour per leg via goal._moveMode ('sprint'|'parkour'), which goToGoal reads into a shared moveProfile(bot, mode). Default stays walk until a hot leg proves a full kick-free cycle; Gate trial legs with a per-goal flag (e.g. goal._sprintTrial read by goToGoal, set only on far legs) so revert is a single flip and near legs stay walk-only. Default stays WALK-ONLY everywhere until that trial passes a full kick-free cycle; (9) chunk_batch_received ack feedback loop — mineflayer's weighted-average round-trip collapses to ~0ms on fast loopback so 7/avg reports hundreds of chunks/tick, and each ack makes PlayerChunkSender fire MORE chunks -> more batches -> positive feedback loop (walk-death: 33 acks in the fatal window with zero AI actions running). Rate-clamping alone is insufficient. FIX in blocks.js chunk_batch_finished: throttle to max 1 ack per 500ms AND report a modest chunksPerTick (8). Skipped acks are simply dropped (vanilla only acks when its renderer is ready, a few per second). World still loads, at a pace a 1-OCPU tick loop survives — fix, not disable.

- 26.3 clientbound position SHAPE (protocol.json packet_position): {teleportId varint, x/y/z f64 ABSOLUTE base, dx/dy/dz f64 DELTAS, yaw/pitch f32, flags: PositionUpdateRelatives bitflags u32 [x, y, z, yaw, pitch, dx, dy, dz, yawDelta]}. There is NO legacy bitmask on 26.3 — flags is always the 9-flag object. Correct resolution: position = packet.x/y/z, then add ONLY the deltas whose dx/dy/dz flags are set; rotation is absolute unless yaw/yawDelta/pitch flags mark it relative (fold onto current entity angles then). The old mineflayer handler read packet.x as absolute-or-relative and resolved pos.x+packet.x for 'relative' folds — on 26.3 that adds garbage (or NaN) onto an absolute base. Same for clientbound player_rotation {yaw f32, relativeYaw bool, pitch f32, relativePitch bool}: a relative turn must FOLD onto the current entity yaw, never overwrite it (overwrite snaps her head to ~0 on every server nudge). NaN-sanitize every piece (base, each delta, yaw, pitch) — one non-finite delta must never poison the whole position.
- 26.3 teleport_confirm poisoning: resolving relative flags against stale client-side entity position can echo coords tens of blocks from truth (walk-death log: d70 position_look 6ms after a confirm nobody asked for). Jar truth (handleAcceptTeleportPacket) snaps lastGood to the confirm's xyz, so one bad echo poisons the movement baseline and the next real move reads as moved-wrongly. FIX: echo the server's verbatim absolute x/y/z/yaw/pitch, never client-side relative math; skip the confirm when no teleport is pending. Sniff the server's teleport shape with a raw unauthenticated client BEFORE touching confirm logic — server `position` events arrive pre-auth, so a 25-line probe logging {teleportId, x, y, z, yaw, pitch, flags} reveals whether spawn placement is absolute (all flags false) or relative, with zero auth needed. This distinguishes a confirm-content bug from an echo-bookkeeping bug before editing. Four hard sub-rules, each verified by a live failure: (a) NEVER send an id-only/truncated confirm — ServerboundAcceptTeleportationPacket is a 6-field Record (id, x, y, z, yRot, xRot) and a truncated packet the jar can't decode kills instantly at spawn (insta join-leave loop); (b) confirm each teleportId ONCE — the jar kills with invalid_player_movement when a confirm id != awaitingTeleport, and re-confirming an already-acked id trips exactly that (walk-death showed 3 confirms in 70ms); (c) NaN-sanitize every field — at fresh login bot.entity.yaw/pitch can be undefined and NaN fails the jar's containsInvalidValues check -> instant kick before spawn. (d) On ABSOLUTE teleports (all flags false = spawn placement), sync lastSentYaw/lastSentPitch to the SERVER's yaw/pitch (what the echo actually sent), not the stale pre-login entity angles — otherwise updatePosition sees yaw drift and emits a position_look the server reads as a tens-of-blocks snap (walk-death d75.62 6ms after a confirm). Relative teleports keep the client-side fold.

- Panda set_equipment crash: 26.3 immutable slots list — copy-on-write fix. antifreecam binary dead (OpenSignEditor ctor gone) — rewritten as SignCheck probe.
- Reliability false-crash attribution: the in-flight crash marker is cleared on clean `exit`, but systemd stop/restart sends SIGTERM, which does NOT fire `exit` — every manual restart while an action ran orphaned the marker, and the next boot falsely +1 crashed a random action (this is how !collectBlocks/!searchForBlock/!goToCoordinates hit CRASH_RETIRE=2 with 98%+ success rates). FIX: clear the marker on SIGTERM/SIGINT too — only a true SIGKILL/OOM orphans it now, which is the real hard-crash signal. Corollary: before trusting any crash count, check attempts/successes — 2 crashes over 500 attempts is restart noise, not a killer.
- Login-noise triage: protodef PartialReadError lines (advancements/recipe VarInt/string decodes) at every login are benign decode noise — never chase them as the kick cause. The signal is the [walk-death] dump's last sends plus kick_disconnect in the inbound packet counts; noise without those is healthy. EXCEPTION with a counting rule: `packet_set_slot -> Slot -> SlotComponent` errors need a per-boot count before dismissal — dozens of identical hits in one boot window mean a real inventory-decode break (bot items() stays empty while RCON shows items); a handful (single digits, mixed with advancements/VarInt noise) is the normal login profile. Settle it with one line, not a theory: log client-side items() next to the RCON gear-up line — matching counts close the case with no protocol.json patch. Fatal counterpart, triage by packet name not family: `array size is abnormally large` on update_light is stream desync, not login noise — it kills the connection (exit 1, systemd restart). When counts mismatch with dozens of identical SlotComponent hits, diff the generated def: compare SlotComponentType mapper entry count against SlotComponent switch field count; switch-only fields with no mapper id are suspect, never real until proven: check the server jar's component field list first (`javap -p` count) — phantom defs absent from the live registry (map_color, swing_animation observed) must be dropped from the switch, never given invented mapper ids, since invented ids shift every later id and break all Slots worse. Equal counts do NOT clear the mapper either — an alpha-sorted mapper at matching counts still breaks every Slot, so verify ORDER via bytecode even when counts agree. Never fix a SlotComponent mapper/switch skew by alpha-sorting or by guessing orphan ids: the mapper must equal the live server's DataComponents REGISTRATION order. Extract it with `javap -c -p` on the server jar's DataComponents class and read the `// String <name>` lines in putstatic sequence (that sequence IS the registry order); map truncated names (villager/variant, wolf/collar, cushion/color) to full component names, keep the canonical order in assets/slotcomponent-122-order.txt, force mapper to it in all protocol.json copies (assets source + both node_modules copies) plus a marker-idempotent slot122 lock step in fix-*.py so reinstalls cannot regress, then restart and verify Slot errors gone plus client items() non-zero — error count alone never justifies the edit, mapper-vs-switch diff plus the client-items diag does.
- Loop-suicides (bot killing itself, NOT server kicks): the bot must NEVER cleanKill itself on stuck/navigation failure — a still-stuck moment becomes a hard systemd restart loop. - NaN on the wire is an instant containsInvalidValues kick anywhere, not just teleport_confirm: a position_look with yaw:null/pitch:null (digDown start, stale pre-login entity angles) kills the same way a truncated confirm does. FIX: NaN-sanitize EVERY movement-body field in sendPacketPosition/sendPacketPositionAndLook/sendPacketLook before the write (skip the send when yaw/pitch/x/y/z is not finite) — never only the confirm path. AND guard the INBOUND clientbound position handler's relative folds the same way: a relative server teleport resolves against the current entity position, so one NaN position poisons every later fold (NaN+dx stays NaN) and pathfinding plans NaN nodes forever while the server shows her frozen — fall back to the packet's absolute value, never NaN. Contain NaN at every LOCAL propagation point too, not just the wire: a single NaN entity position is cloned by every later physics tick, folded by every later teleport, planned into NaN pathfinder nodes, and recentered by fullStop (floor(NaN) is NaN) — so one bad tick becomes a permanent frozen-but-'walking' state. FIX: split physics simulate/apply and skip the apply when the sim result is non-finite (log from-pos/vel/yaw/control once per ~30s to identify the source); drop NaN yaw/pitch in bot.look (pathfinder drives look with NaN dx from poisoned nodes); never apply a non-finite clientbound position (keep last-good, log the raw packet once); bail out of pathfinder fullStop's recenter when position is non-finite. TEMP debug harness that proved this: 5s [phys-dbg] dumps (frozen flag, local pos, chunk ok/NULL, isMoving, goal class, send counters pos/poslook/look/tickend, skip counters noent/nochunk/frozen/dead) plus [nan-src] one-shot source logs — remove the harness after diagnosis, keep the guards.
